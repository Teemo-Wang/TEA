## 〇、V0.3 相比 V0.2 改了什么

| 维度 | V0.2 | V0.3 |
|---|---|---|
| 目标用户 | 项目发起者本人（懂 Git 的开发者视角） | **各行各业、不太懂代码、想靠 AI Agent 团队做出自己产品的人** |

## 一、产品定位

### 1.1 一句话

> **让不懂代码的人，也能像带团队一样，指挥一组 AI Agent 把自己的产品做出来——看得见谁在干什么、听得懂进度、拿得到成果，并且不会把项目搞坏。**

### 1.2 目标用户

各行各业、有产品想法、不太懂或完全不懂代码的人：设计师、策划、创业者、教师、研究者等。
**典型用户画像：** 本项目发起人——资深视觉设计师，完全不懂代码，希望靠 AI Agent 团队做出自己的产品项目。

这类用户的共同点：

- 看不懂 Diff、终端日志和报错堆栈；
- 能判断"效果对不对"，但不能判断"代码好不好"；
- 手上可能有多个 Agent / 模型账号，但不清楚各自适合干什么；
- 最怕的是：AI 把项目改坏了、不知道进行到哪、成果散落各处找不到。

### 1.3 终局愿景

| 组成 | 参考 | 用户得到什么 |
|---|---|---|
| 项目管理 | Paperclip 式任务 / Agent 编排 | 任务、进度、审批、预算都有据可查 |
| 角色可视化 | 腾讯 Marvis 式虚拟办公室 | 一眼看出哪个 Agent 在工作、在等、卡住了 |
| 项目讨论组 | Discord 式群聊 | 用说话的方式提需求、@某个 Agent 派活 |
| 智能团队管理 | 项目经理自动组队 | 项目经理根据能力表推荐团队，用户拍板 |

**多项目身份：** 同一个 Agent 可以加入多个项目，但在每个项目里有**独立的身份、上下文和记忆**，项目之间默认不共享私有数据。

## 二、设计原则

1. **先真实，再好看。** 先保证任务真的能执行、状态可信，再做角色动画。
2. **用户看效果，系统管代码。** 用户面对预览和大白话；Git、Worktree、Diff 在后台保证安全，技术用户可在"高级视图"中查看。
3. **AI 提议，人来拍板。** 拆活、派活、合并、高风险操作都必须经用户确认；首版不做全自动。
4. **不知道就说不知道。** 状态只来自可验证信号；推断的标 `inferred`，确认不了的标"未知"，项目经理的汇报同样遵守。
5. **成果不丢、好找。** 所有产出按项目归档，可追溯到是哪个任务、哪个 Agent、哪次执行产生的。
6. **复用优先，少改底座。** 优先复用成熟开源项目，通过适配层接入，不维护两套任务事实源。

## 三、核心概念

| 概念 | 面向用户的说法 | 说明 |
|---|---|---|
| Project | 项目 | 独立空间：讨论组、成员、任务、产出、记忆 |
| Agent 档案 | Agent | 全局信息：运行框架、供应商、模型、能力 / 速度 / 成本标签 |
| 项目成员身份 | 项目里的角色 | 某 Agent 在某项目中的名字、职责、上下文、记忆；按 `projectId` 隔离 |
| 项目经理 | 项目经理 | 特殊成员：拆活、推荐人选、解释进度、汇总结果 |
| Task | 任务 / 活儿 | 主任务 + 一层子任务（沿用 V0.2） |
| Attempt | 第几次尝试 | 每次执行或返工都是新的 Attempt，不覆盖历史 |
| Artifact | 产出 | 代码、图片、文档、预览链接等，归档到项目 |

核心关联（沿用并扩展 V0.1 / V0.2）：

```text
Project
  ├── Member（用户 / Agent 的项目身份）
  ├── Discussion / Message ──引用── Task
  ├── Task
  │    └── Attempt
  │         ├── Provider Session / Invocation
  │         ├── Execution Event
  │         ├── Check Result（测试 / 预览 / 审查 Agent 意见）
  │         ├── Artifact
  │         └── Change Set + Result Commit（后台）
  ├── Artifact Library（项目产出库）
  └── Project Memory
```

聊天消息不等于执行记录：讨论组只通过引用关联任务，进度以执行事件为准。

## 四、核心用户流程（P1 目标）

1. 用户在项目讨论组里用自然语言说需求。
2. **项目经理**整理出一份"工作计划"：拆成几件子任务、每件推荐谁做、为什么推荐、预计快慢和成本、先后顺序。
3. 用户**查看并修改**计划（换人、删减、调整顺序），点击确认。**未确认前什么都不执行。**
4. 用户也可以跳过项目经理，直接 `@某个 Agent` 派一件明确的小活。
5. 平台在后台为每次执行创建隔离工作区，Agent 开始干活；讨论组和任务卡片实时显示状态。
6. 完成后，平台收集产出与证据（预览、截图、测试结果、文件变更），可选让**审查 Agent** 看一遍代码。
7. **项目经理用大白话汇报**：做了什么、怎么看效果、哪些验证过、哪些没验证、有什么风险。
8. 用户看效果后选择：**接受 / 继续改 / 重来 / 放弃**。
9. 用户最终确认后，平台才把结果合入项目正式版本；有冲突则停下来，由项目经理解释并给出选项。
10. 所有产出自动归档到项目产出库。

## 五、功能设计

### 5.1 项目空间与讨论组

- 创建 / 切换项目；每个项目一个讨论组（P1 不做多频道）。
- 消息类型：用户消息、Agent 回复、项目经理计划卡、任务状态卡、汇报卡、审批卡。
- `@Agent` 直接路由给指定成员，**不必每条消息都经过项目经理模型**（沿用 V0.1）。
- 任务卡片与消息互相跳转。
- 首版不做 `@全体`、多频道、从闲聊中自动建任务。

### 5.2 项目经理（受控）

**职责：** 帮用户拆活、推荐人选、解释进度、汇总结果、翻译技术问题。

**边界：**

- 只能**提议**，拆活计划和派活必须用户确认后才执行；
- 不能自行合并、删除、发布，也不能绕过审批；
- 汇报必须引用平台证据（事件、测试、预览），区分"已验证 / Agent 自述 / 推断 / 未知"，不得把未验证的说成完成；
- 项目经理由哪个 Agent / 模型担任：**待定**，由用户在项目中选择。

### 5.3 Agent 能力表与派活推荐

每个 Agent 档案记录三层信息（沿用 V0.1）：**运行框架 → API / 供应商 → 实际模型**，以及接入能力矩阵（启动、流式事件、取消、Session 恢复、Token、实际模型等，取值 `supported / partial / unsupported / unknown`，沿用 V0.2）。

在此基础上新增**用户可维护的经验标签**：

| Agent（示例） | 擅长 | 速度 | 质量 / 稳定性 | 成本 / 额度 |
|---|---|---|---|---|
| DSH（DeepSeek Harness） | 快速出 Demo | 快 | 正式版 bug 偏多 | 待填 |
| Codex | 正式开发、改 bug | 慢 | 准确 | 额度有限 |
| Grok API | 接入方便 | 待填 | 容易掉线 | 价格偏高 |

> 以上为发起人的使用经验示例，**不是评测结论**；开源版本默认表可留空或仅作示例，由每位用户自己维护。

推荐规则：

- 项目经理结合任务性质（Demo / 正式版 / 文案 / 图片…）、标签、当前额度和 Agent 在线状态给出推荐，并**写明理由**；
- 用户可以**随时人工覆盖**，覆盖记录保留；
- P2 之后可考虑基于历史执行结果（成功率、返工次数、耗时）给出参考数据，但**只展示真实统计，不编造评分**。

### 5.4 结果审查：看效果 + 大白话

用户看到的审查页按顺序展示：

1. **效果预览**：可运行的预览、截图、生成的图片或文档。具体支持哪些项目类型的预览：**待定**（P1 先选 1～2 类）。
2. **项目经理汇报**：一段大白话 + 验证清单（✅ 已由平台验证 / 🟡 Agent 自述 / ⚪ 未验证）。
3. **审查 Agent 意见（可选）**：由另一个 Agent 检查代码质量与风险；其结论只是**建议**，不能代替用户确认，也不能自动放行合并。
4. **高级视图（折叠）**：时间线、变更文件、Diff、测试命令与退出码、Base / Result Commit——给懂技术的用户或社区贡献者。

测试命令由平台实际执行并记录，不只依赖 Agent 口头上报（沿用 V0.2）。

**内部状态 → 用户可见说法（示例）：**

| 内部状态 | 用户看到 |
|---|---|
| Attempt `Running` | 正在做 |
| Attempt `Waiting` | 在等前面的活完成 |
| `AwaitingReview` | 做完了，等你看效果 |
| `NeedsMerge` | 和其他改动有冲突，需要你决定 |
| `Interrupted` | 意外中断了，可以重来 |
| `unknown` | 系统无法确认 |

### 5.5 产出归档

- 每个项目有统一的**产出库**：代码版本、图片、文档、预览、汇报，按任务和时间可筛选、可搜索。
- 每个产出记录来源：项目、任务、Attempt、Agent、时间、是否被用户接受。
- 被接受的产出标为"正式"，未接受的保留为历史，不混在一起。
- 非代码产出（尤其大图片）的版本存储方式：**待定**（Git / Git LFS / 平台自管文件库，P0～P1 评估）。

### 5.6 安全底层（后台运行，沿用 V0.2）

以下规则不变，只是不再要求用户理解：

1. 每个 Attempt 独立的 Branch、Worktree、Base Commit；Agent 不直接改主工作区和正式分支。
2. **平台统一创建 Result Commit**；无变更、测试未运行、Commit 失败都要明确显示。
3. 有依赖的任务通过**主任务临时集成分支**获得已接受的上游成果。
4. 返工分为"继续改"（基于上次成果）和"重来"（从有效基线重新开始）。
5. **只有用户确认后才合并**；合并前检查目标分支最新状态，**冲突即阻塞**，禁止自动覆盖。
6. Worktree 清理幂等，存在未记录改动时禁止清理；重启后校准遗留进程和工作区。
7. 状态三维分离：Task / Attempt / Review-Merge。
8. SSE 事件带持久 ID，支持断线重连、重放、去重。
9. 安全定位仍是"**可信 Agent 环境下的协作隔离**"，Worktree 不是沙箱；默认最小化传给 Agent 的环境变量与密钥；界面如实说明未提供容器、网络隔离和 Secret Broker。

### 5.7 角色可视化（P2）

- 每个项目成员有形象，状态映射**真实事件**：待命、规划、工作、等待、等审批、受阻、完成、异常（沿用 V0.1 状态表）。
- 点击角色查看当前任务、最近动作、产出，可追加指令或暂停。
- 进度百分比按任务完成与验收计算，**不按 Agent 活跃程度估算**。
- 可视化模块是否复用 Pixel Team Studio 等项目：**待 P0/P2 验证**（能力、许可证、维护状态）。

### 5.8 智能组队与受控委派（P3）

- 项目经理根据需求和能力表推荐**项目核心团队**和**临时成员**，用户确认后组队；任务结束后释放临时成员，保留成果与审计记录。
- Agent 可提出委派请求 → 平台检查权限、依赖、预算 → 创建子任务 → 目标 Agent 执行 → 回传结果（沿用 V0.1）。
- 必须限制：委派深度、并行数、重试次数、时长、Token / API 预算、可访问文件范围。
- 合并、高风险操作和超预算仍需用户确认。

## 六、插件体系

> 本章与 MVP-0 规划书第 6 节「最小插件机制」保持一致；首版具体字段、权限名和验收以 MVP-0 为准。

### 6.1 定位：开源生态的核心扩展点

- 参考 DSH 可自定义插件 / 技能卡的思路：**用户按自己的需求自行制作插件**，不必等官方更新——想接入一个新 Agent、想固定一种常用任务的做法，都可以做成插件。
- 插件是本项目开源后**社区参与的主要入口**：各行各业的用户可以把自己领域的做法（例如某类文档、某种设计流程）沉淀为插件并分享。
- 平台本体只保留任务、执行、审查、归档、安全等核心能力；"接什么 Agent、做什么类型的活"尽量通过插件扩展。

### 6.2 插件长什么样

- **插件 = 一个文件夹 + 一份 `plugin.json` 清单。** 平台启动时自动扫描插件目录发现插件，在「插件」页可启用 / 停用、重新扫描。
- 清单记录：唯一 `id`、中文显示名、版本、插件接口版本（`apiVersion`）、类型、入口文件、所需权限、说明；不同类型可带各自的配置段（字段细节见 MVP-0 第 6.3 节）。
- **内置 Agent 也用插件格式实现**（如内置的 Codex、DSH、API 类 Agent 适配器），既证明插件机制真的可用，也让社区插件和官方能力处于同一套规则下。
- 清单不合法或加载失败的插件单独标红显示原因，**不影响其他插件和应用启动**。

### 6.3 插件类型（分阶段演进）

| 阶段 | 类型 | 用途 | 是否含代码 |
|---|---|---|---|
| **首版（MVP-0 / P0）** | Agent 适配器 | 接入一个新的 CLI 或 API Agent，实现平台统一的适配器接口 | 含代码 |
| **首版（MVP-0 / P0）** | 任务模板 / 技能 | 预设一种任务：提示词模板 + 需要用户填写的变量 + 期望产出类型 | 纯数据，不执行代码 |
| 后续可选 | 产出预览器 | 让更多类型的产出能在平台内"看效果"（如 3D 模型、特定文档格式） | 待评估 |
| 后续可选 | 工具 / 工作流节点 | 连接外部创作工具或工作流，如 ComfyUI、Blender | 待评估 |
| 后续可选 | 角色形象皮肤 | 为 P2 角色可视化提供可替换的形象 | 以素材为主，待评估 |

后续类型是否做、何时做，按真实需求和前一阶段的验证结果决定，**不在首版承诺**。

### 6.4 权限与安全边界

- **默认最小权限**：插件必须在清单中声明所需权限（如读 / 写项目文件、启动外部程序、访问网络、读取某个密钥），**未声明的一律不给**；平台只向插件提供受限的宿主接口，而不是直接暴露全部系统能力。
- **项目目录限制**：插件读写文件、启动进程都只能在当前项目文件夹内；只拿到白名单环境变量和已声明的密钥，密钥不写入日志和事件。
- **如实声明：首版不是沙箱。** 含代码的插件（如 Agent 适配器）首版与平台同进程运行，权限是"约定 + 宿主接口限制"，并不能阻止恶意代码；界面明确提示"只安装你信任的插件"。纯数据的任务模板风险较低。
- 真正的沙箱隔离与开源分发后的安全底线一并评估（见第十一章第 11 条）。

### 6.5 放到后续阶段的能力

以下能力**首版不做**，在插件机制被验证可用、准备开源发布时再评估：

- 插件市场（浏览、搜索、评价、分享）；
- 远程安装 / 一键更新；
- 插件签名校验与来源可信度标识；
- 插件版本兼容管理（`apiVersion` 升级时的兼容策略、迁移提示）；
- 沙箱隔离运行含代码的插件。

### 6.6 与 DSH 插件格式的关系

产品负责人希望插件体验接近 DSH 的插件 / 技能卡。**DSH 插件的具体格式目前不清楚，需探测**（清单字段、目录约定、加载方式），在探测结论出来之前，本项目按自身 `plugin.json` 格式实现，**不假设、不臆造与 DSH 兼容**；是否向其靠拢或提供兼容层，见第十一章待确认问题。

## 七、技术方向（候选，待验证）

```text
前端（讨论组 / 审查页 / 产出库 / 可视化）
        ↓
平台 API 与集成层（项目经理、推荐、预览、归档、事件投影）
        ↓
控制面候选：Paperclip（任务 / Agent / 审批 / 预算）
        ↓
薄编排与 Adapter 层（Attempt、Worktree、Result Commit、事件规范化）
        ↓
Agent：Codex、DSH、API 类 Agent（如 Grok API）……
```

| 候选项目 | 设想用途 | 当前状态 |
|---|---|---|
| [Paperclip](https://github.com/paperclipai/paperclip) | 控制面：项目、任务、Agent、审批、预算 | **P0 决策门，待验证** |
| [Pixel Team Studio](https://github.com/NJ-A2A/pixel-team-studio) | 角色与办公室可视化 | 参考 / 复用候选，待验证 |
| [Agent Standup](https://github.com/Atoll92/agent-standup) | Session 状态、执行日志可视化 | 参考候选，待验证 |
| [Easy Vibe Kanban](https://github.com/toby1123yjh/easy-vibe-kanban) | ACP 接入、多 Agent 工作流 | 参考候选，待验证 |
| [Hindsight](https://github.com/vectorize-io/hindsight) | 后续记忆增强 | 非首版依赖 |

**原则：** 只保留一个任务事实源；不大规模修改第三方核心源码；**因为本项目要开源发布，所有复用项目都必须先确认许可证兼容**。

## 八、阶段计划与验收标准

> 运行平台待定：P0 在开发者现有环境中验证，正式支持哪些操作系统另行决定。

### P0｜底座与单 Agent 真实执行验证

**内容：**

1. **Paperclip 决策门**：验证数据模型、Attempt 表达、依赖、审批、Artifact、Adapter、事件订阅、重启恢复、Worktree 支持、**许可证**。缺少少量非核心能力→薄层补齐；缺少 Attempt、事件持久化、Adapter 控制、状态恢复等核心能力→No-Go。
2. **Codex 单 Adapter 闭环**：Worktree → 启动 → 状态 → 取消 / 超时 → 测试 → 变更采集 → Result Commit → 审查 → 用户确认合并。
3. **可靠性**：异常退出、应用重启、事件重放与去重、孤儿进程、遗留 / 脏 Worktree、冲突阻塞。
4. **第二个 Agent**（DSH 或 API 类 Agent，顺序待定）：能否实现同一 Adapter 契约，能力差异如实记录。
5. **最小"看效果"验证**：至少一种项目类型能生成可供非技术用户查看的预览或截图。
6. **最小插件机制**（见第六章，细节以 MVP-0 为准）：插件发现 / 清单校验 / 启用停用；首版两类插件（Agent 适配器、任务模板）；内置 Agent 适配器以插件格式实现；探测 DSH 插件 / 技能格式并记录结论。

**验收标准：**

- 输出 Paperclip 能力矩阵、缺失清单、复用边界、许可证结论和 Go / No-Go；
- Codex 闭环：5 个真实任务至少 4 个形成可审查结果并在用户确认后安全合并；
- 插件：内置 Agent 均通过插件格式加载；停用某 Agent 插件后该 Agent 不可派活、重新启用后恢复；按说明新建一个任务模板插件，无需改平台代码即可出现在模板菜单并使用；故意写坏的 `plugin.json` 只显示"加载出错"，不影响其他功能；未声明的权限拿不到；DSH 插件格式探测结论（含"未知"）已记录；
- 以下场景 **100% 通过**：不污染主工作区；未经确认不合并；冲突不误报成功、不自动覆盖；重启后记录不丢；取消能结束完整进程树；有未记录改动的 Worktree 不被清理；重复事件不重复入库。

### P1｜讨论组 + 项目经理拆活 + @派活 + 大白话审查 + 产出归档

**内容：** 5.1～5.6 全部最小版；Agent 能力表（含用户自维护标签）与推荐；项目固定说明 + "项目经理提议、用户确认后写入"的项目记忆；同一 Agent 可加入多个项目且身份隔离；插件页（含权限说明与"只安装你信任的插件"提示）与面向普通用户的中文插件制作指南。

**验收标准：**

- 由一位**不懂代码的用户**（可由发起人本人担任）在真实项目中完成 5 个需求，至少 4 个走通：
  `讨论组提需求 → 项目经理出计划 → 用户确认/修改 → 执行 → 看预览 + 大白话汇报 → 接受 → 确认合并 → 产出入库`
- 全程**无需打开终端、无需阅读 Diff**；
- 项目经理计划**未经确认不会执行**（100%）；汇报中每条结论都标注证据来源，无"未验证却称完成"的情况；
- 用户能修改推荐并覆盖派活，覆盖被记录；
- 任一产出可在 3 次点击内找到并追溯到任务和 Agent；
- 同一 Agent 在两个项目中的上下文和记忆互不可见（100%）；
- 一位不懂代码的用户照着插件指南，能独立做出并使用一个自己的任务模板插件；
- P0 的安全场景继续 100% 通过。

### P2｜角色可视化（真实事件驱动）

**验收标准：**

- 角色状态与真实执行事件一致，抽查无"假忙碌"；未知状态显示为未知；
- 用户不进日志页即可发现正在工作、等待审批、受阻或出错的 Agent；
- 主要状态更新延迟目标约 3 秒以内；
- 讨论组、任务卡、产出库、角色之间可互相跳转。
- （可选）若引入角色形象皮肤或产出预览器插件：替换 / 停用插件不影响状态显示的真实性，加载失败时回退到默认形象或默认预览。

### P3｜智能组队与受控委派

**验收标准：**

- 一项复合需求由项目经理推荐团队并拆给至少 3 个 Agent，用户一次确认后按依赖执行，失败能重试或上报；
- 委派深度、并行数、重试次数、预算上限均生效，超限进入审批而非静默继续；
- 每次组队与委派都记录理由、证据和结果；
- 合并与高风险操作仍 100% 需要用户确认。

### 后续｜插件生态与开源发布（P3 之后，按需评估）

**内容（均为候选）：** 工具 / 工作流节点插件（如 ComfyUI、Blender 连接）；插件市场、远程安装、签名校验、插件版本兼容管理；含代码插件的沙箱隔离。

**验收标准（届时细化）：**

- 插件接口版本升级时，旧插件要么继续可用，要么明确提示不兼容及处理办法，不出现静默失效；
- 远程安装的插件安装前展示来源、签名校验结果和所需权限，由用户确认后才安装；
- 任何插件（含工作流节点）发起的外部操作仍受项目目录、权限声明和用户确认规则约束。

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 非技术用户无法判断代码质量，"看着能跑"但隐患多 | 平台实测 + 可选审查 Agent + 验证清单；明确告知哪些未验证 |
| 项目经理"说得好听"，汇报失真 | 汇报必须引用平台证据并标注来源；不允许无证据的"已完成" |
| 开源后用户环境更杂、Agent 可信度更低 | 如实声明安全边界；最小化密钥传递；容器 / 沙箱列为后续评估 |
| Agent 兼容性差异大 | 独立 Adapter + 能力矩阵；不假设统一能力 |
| 第三方项目许可证或维护风险 | P0 先查许可证；通过接口和适配层接入，减少源码侵入 |
| 项目间数据泄露 | 按 `projectId` 隔离成员身份、上下文、记忆、文件 |
| 成本失控、循环委派 | 预算、深度、并行、重试、时长上限；超限需审批 |
| 多 Agent 文件冲突 | Worktree 隔离 + 临时集成分支 + 冲突即阻塞 |
| 能力标签主观、过时 | 标签由用户维护并显示更新时间；统计数据只用真实记录 |
| 非代码产出体积大、版本难管 | P0～P1 评估存储方案，先保证可找、可追溯 |
| 可视化喧宾夺主拖慢进度 | 可视化放在 P2，且只映射真实事件 |
| 恶意插件窃取密钥、越界读写或破坏项目 | 最小权限 + 清单声明 + 项目目录限制 + 密钥按声明发放；如实声明首版不是沙箱并提示"只安装你信任的插件"；签名校验与沙箱放后续阶段 |
| 低质量插件导致出错、卡死或产出质量差 | 清单校验，加载失败只影响该插件；插件页显示来源、版本、权限；可随时停用；产出仍走平台审查与用户确认 |
| 插件接口变更导致社区插件失效 | 清单带 `apiVersion`；接口变更时提供兼容期或明确的不兼容提示；内置 Agent 走同一插件格式，接口改动先在内置插件上验证 |

## 十、明确不做（至 P1 结束前）

- 全自动执行（无需用户确认的拆活、派活或合并）；
- 测试通过后自动合并；
- Agent 自主委派、自动组队（P3 再做，且受控）；
- 多层子任务、任意复杂 DAG；
- 多频道、`@全体`、从闲聊自动建任务；
- 多用户账号、团队协作、云端托管执行；
- 多项目同时调度、跨项目任务、跨项目私有记忆共享；
- 自动长期记忆、全局知识库、向量检索；
- 精确费用核算（只展示可采集的用量，其余标未知）；
- 针对恶意 Agent 的强安全沙箱；
- 移动端；
- 完整虚拟办公室动画（P2）。

新增需求若不直接服务于"**拆活可控、执行真实、结果看得懂、成果不丢、项目不被搞坏**"，默认不进入 P1。

## 十一、仍待确认的问题

1. **运行平台**：首发支持哪些操作系统？是否要考虑桌面安装包形态？
2. **首个验收项目**：用什么真实项目做 P0 / P1 验收？
3. **项目经理**由哪个 Agent / 模型担任？是否允许每个项目单独选？
4. P0 第二个接入的是 **DSH 还是 API 类 Agent（如 Grok API）**？
5. P1 先支持哪些**预览类型**（网页、游戏、图片、文档……）？
6. **审查 Agent** 默认开启还是可选？用哪个 Agent？
7. 非代码产出的**存储与版本方案**。
8. Agent 能力表的**默认内容**：开源版是否附带示例？未来是否支持社区共享？
9. 本项目自身的**开源许可证**，以及与 Paperclip 等复用项目的兼容性。
10. 界面语言：首发中文、英文还是双语？
11. 开源分发后的**安全底线**：何时引入容器 / 沙箱？
12. 用量与额度数据能否从各 Agent 采集（不能则只能由用户手填）。
13. 正式项目名称是否沿用 "AI Project Team OS"。
14. **DSH 插件 / 技能格式**是什么样、本项目 `plugin.json` 是否应与其兼容或向其靠拢：**需探测**（清单字段、目录约定、加载方式），探测不到则按本项目格式实现，不臆造兼容。
15. 后续插件类型（产出预览器、工具 / 工作流节点、角色形象皮肤）的优先级与引入阶段。

此外沿用 V0.2 的 P0 核验项：DSH 准确仓库 / 版本 / CLI 与机器可读输出；各 Agent 对取消、Session 恢复、工具事件、Token、实际模型的支持；完整进程树终止；子模块 / LFS / 嵌套 Worktree 支持范围；集成分支冲突的人工处理入口；事件、日志与产出的保留周期。

## 十二、结论

V0.3 把产品从"开发者自用的代码 Agent 控制台"调整为"**让不懂代码的人带领 AI 团队做产品的开源平台**"。底层安全设计不变，变的是用户界面：用讨论组提需求，由项目经理拆活和解释，用户看效果并拍板，成果统一归档。

研发顺序：

> **先验证底座和单 Agent 真实执行（P0）→ 再做看得懂、可控的协作闭环（P1）→ 再做真实事件驱动的可视化（P2）→ 最后做受控的智能组队与委派（P3）。**

只有 P0 证明任务事实源、Adapter 控制、隔离执行、事件恢复、安全合并和最小预览均可行，才进入 P1。
